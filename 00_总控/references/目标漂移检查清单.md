# 目标漂移检查清单（DRIFT_CHECK）

> 时机：施工过程中每个新动作/能力/目录/系统修改/范围扩展之前。作用：与《任务理解合同》对账，防止目标漂移与擅自扩展。

## 一、每个动作执行前的四个问题

| 问题 | 若答案为否 |
| ---- | ---- |
| 当前动作是否服务于合同中的目标（user_real_goal/final_deliverable）？ | 是漂移 → 阻断 |
| 当前动作是否属于本轮 work_scope？ | 是漂移 → 阻断 |
| 当前动作是否违反 forbidden_modify / forbidden_tools / key_constraints？ | 与禁止项冲突 → 阻断 |
| 当前动作是否扩大了未授权的权限或修改了未授权区域？ | 越权 → 阻断 |

另加：是否新增了用户没有要求的能力？是 → 阻断（禁止“顺手优化”）。

## 二、触发 BLOCKED 的典型情形

- “顺便更方便”“更完整”“以后可能需要”“最佳实践”“我认为这样更好” 的扩容理由
- 合同写明“Harness 不允许修改”，模型仍为方便接入而改 Harness
- 新增目录、系统、依赖、权限未列入 work_scope / allowed_modify / allowed_tools

## 三、处置流程

```text
发现疑似漂移/冲突
  ↓
对照任务理解合同定位冲突字段
  ↓
记入 drift_check_log（含 CONSTRAINT_CONFLICT / DRIFT_DETECTED + 证据）
  ↓
→ 若属于重大变更：回到 UNDERSTANDING，更新合同并经用户确认后再继续
→ 否则：BLOCKED，请求人工介入
```

## 四、禁止“先施工再解释”

任何动作一旦与合同冲突，必须先阻断并记录，不得继续施工后再向用户解释。事后道歉不是验收机制。

## 五、Evidence

每次 DRIFT_CHECK 产生 `drift_check_log`（时间戳、动作、合同字段、冲突类型、证据引用）。冲突清单由 `constraint_conflicts` 证据类型承载（`06`）。

# 企业 AI 可信交付 Skill：管理者说明

> 当前正式版本：`v3.0.9`

## 一句话说明

`enterprise-ai-project-delivery` 不是替企业回答问题的另一个聊天机器人。

它是一层放在模型和企业正式结果之间的**可信交付控制层**：让用户只说想完成什么，由 AI 理解、规划、选择当前 Harness 中可见且获授权的成熟能力来完成工作；但失败、权限、变更和“完成”不能只靠模型自己说了算。

## 企业正在面对的真实问题

大模型已经能写代码、整理报告、调用工具、生成文件，但它经常出现一个企业无法接受的问题：**它做错了、漏了、环境坏了，仍可能继续执行，甚至说“已经完成”。**

于是员工不得不坐在电脑前反复检查、纠错、催停和返工。AI 看似提高了产出，实际却把“项目监工”的负担交给了人。

## 这个 Skill 解决什么

它把 AI 的工作从“模型给出一个回答”变成“可被企业接收的一次交付”。

```text
用户说目标
  → AI 理解真实需求与当前项目
  → 形成用户可审阅、可修改的真实工作计划
  → 选择当前 Harness 可见、兼容、获授权的能力
  → 持续执行并记录真实结果
  → 失败：定位、有限恢复、换安全思路
  → 外部条件或业务决定：暂停并清楚交接
  → 恢复后重验原失败与回归
  → 只有 Evidence 齐全才允许说完成
```

## 最核心的能力

### 1. 不让用户当 AI 的项目监工

用户不需要先拆成一堆技术步骤，也不需要自己挑选每个工具或 Skill。用户说明目标即可；系统只在确实会改变方案的地方提问，并将内部治理隐藏在正常的项目交付体验之后。

### 2. 不让 AI 的“我完成了”直接等于企业完成

每个验收项必须有当前项目、当前候选版本上的真实 Evidence，例如测试输出、文件、命令、日志、截图或外部系统结果。模型的文字说明不是 Evidence。

### 3. 失败时不死磕，也不装作没事

失败会被冻结为事实。第一次恢复未通过原 blocker 后，下一次自动切换另一种安全恢复顺序：

```text
根因优先  ↔  先隔离影响再找根因
```

每次恢复都必须重新验证原失败点和相关回归。恢复预算耗尽、需要新权限、业务判断或外部系统操作时，系统停止并生成明确的人工接手包，而不是继续猜、继续重试或假装完成。

### 4. 用户始终拥有业务决定权

批准计划、修改需求、暂停、恢复、取消、用户纠错等状态，必须绑定可信 Harness 用户来源。模型不能自己编造“用户刚刚批准了”或“用户要求取消”。

### 5. 能组合成熟能力，但不伪造能力

它不是要替代所有专业 Skill。它会把当前项目需要的能力交给已发现、兼容、验证过且已授权的候选去处理，例如测试、代码审查、浏览器验收、文档、部署等；每次调用都绑定具体 Work Unit，完成后清理临时上下文和权限范围。

## 与普通 Skill 的区别

| 问题 | 普通 Skill | 本 Skill |
|---|---|---|
| 核心作用 | 提供某类知识、提示词或工具步骤 | 管理整个项目交付过程的可信性 |
| 用户需要做什么 | 常要自己决定下一步、挑工具、盯进度 | 先说目标，必要时审阅计划和作业务决定 |
| AI 做错时 | 依赖模型自己发现、承认并修正 | 冻结失败、保留证据、有限恢复、重验 |
| 重复失败 | 容易重复同一种尝试 | 自动切换安全恢复思路；无权修复时暂停交接 |
| “完成”的含义 | 模型认为完成 | 当前 Evidence 支持所有验收项才可完成 |
| 权限与审批 | 常由对话语义推断 | 必须有可信用户/企业来源 |
| 多 Skill 协作 | 可能只是提示模型“去用” | 绑定 Work Unit、身份、版本、权限、结果与 Evidence |

## 与 Superpowers 的区别与关系

[Superpowers](https://github.com/obra/superpowers) 是优秀的软件开发方法论：强调设计澄清、计划、TDD、系统化调试、审查、隔离工作区和完成前验证。

我们已经吸收其适用于工程交付的部分：

- 设计与计划先行；
- 基线检查；
- RED → GREEN → REFACTOR；
- 系统化根因定位；
- Work Unit 复核；
- 完成前真实验证；
- 变更收尾与风险说明。

但两者解决的问题不同：

| 维度 | Superpowers | enterprise-ai-project-delivery |
|---|---|---|
| 主要对象 | 软件开发 Agent 的工程方法 | 企业中任何复杂项目的可信交付 |
| 重点 | 怎样更有纪律地开发软件 | 怎样让 AI 的交付可控、可验收、可追溯 |
| 失败处理 | 系统化调试与修复流程 | 调试之外，还管理恢复预算、外部阻塞、人工接手和恢复重验 |
| 人类决定权 | 主要体现在设计和执行协作 | 计划、变更、暂停、恢复、取消、纠错都受可信来源保护 |
| 完成门槛 | 验证工作完成 | Evidence、权限、未关闭失败和验收项共同决定是否允许完成 |
| 适用范围 | 主要是软件工程 | 软件、数据、自动化、文档、业务流程等多步骤项目 |

可以把它们理解为：

```text
Superpowers：帮助 AI 更像一名有纪律的工程师
本 Skill：让 AI 的项目结果更像一项企业可以接收的交付
```

它们可以协作，不是互相替代。当前 Harness 可见并允许调用 Superpowers 时，本 Skill 可把其中的设计、TDD、调试、审查等能力作为具体 Work Unit 的施工资源；本 Skill 继续负责范围、权限、Evidence、恢复和完成门禁。

## 为什么企业现在需要它

企业真正缺的通常不是“再多一个会回答问题的模型”，而是让 AI 能进入真实工作而不把风险转嫁给员工。

| 企业场景 | 没有可信交付控制时 | 使用本 Skill 后 |
|---|---|---|
| 财务、审核、报表 | 规则变了，AI 可能沿用旧结论 | 变化影响的工作和 Evidence 必须重验 |
| 软件修复 | AI 可能反复修改、反复失败 | 有界恢复、切换策略、回归验证、必要时交接 |
| 需要审批的流程 | 模型可能把一句话误判为同意 | 只有可信来源才能改变人类拥有的状态 |
| 多工具、多 Skill 项目 | 人员要自己判断调用什么、是否清理 | 基于当前可见、兼容、授权候选进行绑定调用和退出 |
| 外部环境故障 | AI 可能绕过配置或声称已修复 | 明确暂停，告诉 Owner 需要什么动作，恢复后重验 |

企业不必先建设一个大平台。更现实的路径是：将它接到一个已有的 Harness、已有的团队 Skill 和一个真实业务流程上，以小范围试点验证是否减少返工、越权、漏验和人工盯守。

## 当前边界：不夸大，也不回避

- 它不保证模型从此不会犯错；它保证错误不能轻易变成“已交付”。
- 它不会凭空发现 Harness 看不见的 Skill；只能从当前可见、合法的候选中选择。
- 它不替用户做业务决定；需要业务判断、权限或外部修复时会停下来交接。
- 不同 Harness 的 Hook、Skill 发现和授权能力不同。主仓库 Core 的能力最完整；某个 Harness 不提供的事件或能力，不会被包装成已经接通。

## 给管理者的最后一句话

> 企业不该要求员工永远守在 AI 旁边纠错。本 Skill 的价值，是让 AI 可以继续做事，但不能把未经验证、未经授权、未恢复的结果包装成企业已经完成的交付。
